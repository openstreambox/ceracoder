# Quality check: test pattern, box counters and far-end analyser

Tools to answer "does every frame arrive, is the sound right, and how late is
the picture?" for a ceracoder stream, without a person watching it.

| Part | Where | What it does |
| --- | --- | --- |
| Test pattern | `pipeline/rk3588/h265_quality_pattern`, `pipeline/generic/x264_superfast_quality_pattern` (generated by `gen_pipelines.py`) | A picture and sound the far end can measure exactly. The existing `h265_test_pattern` stays as it is |
| Pattern clock | `src/gst/quality_probe.c` | ceracoder writes the wall-clock time of frame 0 into the picture before it starts |
| Counters | `src/core/quality_counters.c`, `bindings/typescript/src/quality.ts` | Frames into the encoder, `videorate` repeats and drops, time at the minimum bitrate, capture caps, sender latency, SRT sender stats; written once a second to `$CERACODER_STATS_FILE` |
| Analyser | `analyse.py` | Records the stream (or reads a recording) and prints one plain report |
| Fault runs | `faults/run_faults.py` | Injects known faults on one machine and checks that the report names each one |

## The pattern

Coordinates are in `pattern_layout.py` (for 1920×1080; the analyser scales
them to the decoded size).

- **Frame counter** (bottom row): 20 bits, each a pair of blocks (value, then
  its inverse), least significant bit on the left. Bit *k* is a square wave
  with a period of 2^(k+1) frames, made by a `videotestsrc pattern=blink` at
  fps/2^k. The far end compares the two halves of each pair, so brightness
  and range changes don't matter, and 48×64 px blocks survive heavy
  compression. Wraps after 2^20 frames (9.7 hours at 30 fps).
- **Pattern clock** (two rows above it): the wall-clock time of frame 0 in
  Unix milliseconds, 42 bits, same pair coding. Static for the whole run.
  Frame *n* was made at `epoch + n / fps`. ceracoder switches the pipeline to
  the realtime system clock and picks the base time just before PLAYING, so
  the blocks are right from the first frame. Only pipelines that contain the
  `qp_epoch_*` elements are touched.
- **Readable time**: the frame number as a timecode (`timecodestamper` +
  `timeoverlay`) and the sender's wall clock (`clockoverlay`), top left.
- **Moving content**: a sweeping ball and a noise patch (top right). The
  noise changes every frame, so a frozen or repeated picture is never
  mistaken for a still scene, and it loads the encoder like real detail.
- **Second marker**: a white block, white for the first half of every second.
- **Sound**: 997 Hz left, 1499 Hz right, both at -18 dBFS (sine peak), plus a
  2 kHz, 50 ms beep at -12 dBFS on both channels, centred on each whole
  second (GStreamer centres its ticks on the tick time).
- **Colour bars** in the background: known patches for the range check.

Only stock GStreamer elements are used (base, good, bad), all of which are in
the device image. Cost: on an x86 workstation the pattern's video takes about
0.57 of a core against 0.09 for the old static pattern (compositor base 0.36,
clock blocks 0.11, counter blocks 0.03, text 0.07). Drawing the counter and
clock in C would remove most of it. The RK3588 cost has not been measured.

## Running it

```sh
# receive, record for 60 s and report (needs srt-live-transmit and ffmpeg)
tools/quality-check/analyse.py capture --srt 'srt://:4000?mode=listener&latency=2000' \
    --seconds 60 --out /tmp/qc
# on the sender
CERACODER_STATS_FILE=/tmp/ceracoder-stats.json \
    ceracoder pipeline/rk3588/h265_quality_pattern <receiver> 4000 -c ceracoder.conf
# report again later, adding the sender's stats (one JSON object per line)
tools/quality-check/analyse.py report /tmp/qc/rec.ts --arrivals /tmp/qc/arrivals \
    --srt-stats /tmp/qc/srt-stats.json --sender-stats stats.jsonl [--srtla-stats srtla.jsonl]
```

Example report (clean run of the x264 version over local SRT, latency 1000 ms):

```
591 frames sent, 591 arrived, 0 repeated (0.0%).
No green frames. Sound: no gaps, both channels, 44 ms behind the picture, steady. Keyframes every 2.0 s.
End-to-end delay: 1.45 s from the pattern clock to the decoded picture (95% of frames within 1.56 s).
Where it goes: encoder and sender pipeline 187 ms; network one way (half the SRT round trip) 0 ms; SRT latency buffer (TSBPD 1000 ms) 1000 ms; receiver demux and decode (the rest) 260 ms.
Stream clock: pictures are sent 161 ms ahead of their presentation time (PTS - PCR); a player that follows the stream clock buffers about that much.

Checked and fine: no green frames, no broken pictures, progressive picture, colour range, picture timestamps even, bitrate steady (peak 1.1x typical), channel polarity, clean sound (no clicks or distortion), levels (loudness -16 LUFS, no clipping), no SRT packet loss.
Not judged: the first 3 s and the last 1 s.
```

## Fault runs

`faults/run_faults.py --out DIR` runs every case (about 25 minutes);
`--only a,b` picks some, `--report-only` re-analyses existing recordings and
`--list` shows them. Each case runs the real ceracoder in its own
`unshare -rn` network namespace on the loopback interface, so netem, MTU
changes and the SRTLA bond (`srtla_send` plus `srtla_rec`, with per-link
netem by source address) need no root. Content faults are pipeline edits
(videorate from another camera rate, an all-zero frame through a compositor
input with a pad offset, channel matrices, gain, dropped sound buffers,
relabelled sample rates); two receiver-side cases are made from the clean
recording with ffmpeg.

## What the analyser checks

| Check | How |
| --- | --- |
| Frames sent, arrived, repeated, missing, restarts | Frame counter, per decoded frame |
| Picture standing still | Longest time without a new frame number; `freezedetect` |
| Green and black frames | `signalstats` (whole frame and lower half), `blackdetect` |
| Broken picture (grey or smeared blocks) | The static colour-bar area compared with its usual look |
| Blockiness | `blockdetect` on the noise patch, once a second |
| Interlaced picture | Frame counter read from each field separately (`idet` kept as a passive figure) |
| Colour range | Black and white levels of the counter blocks against the declared range |
| Timestamps, keyframe interval, bitrate peaks | `ffprobe` packets |
| Sound gaps, level, clipping, loudness | `silencedetect` per channel, `astats` per channel, `ebur128` |
| Channels silent, swapped, inverted; wrong sample rate; speed changes | Tone fit per 10 ms window and channel, tone frequency per second, beep phase left vs right |
| A/V offset and drift | Beep centre against the frame whose number is a whole second |
| End-to-end delay and its parts | Pattern clock against the receiver's wall clock at decode, with sender latency, SRT RTT and TSBPD latency |
| Stream clock lead | MPEG-TS PTS minus PCR |
| SRT loss and drops | Receiver `pktRcvDrop`, loss, belated, retransmissions |
| SRTLA links | Per-link bytes and NAKs from `srtla_send --stats-file` snapshots |
| Box counters | ceracoder's stats file: `videorate` repeats and drops, time at minimum bitrate, stuck reader |

## Limits

- Delay across two machines is only as good as their clock sync: NTP on a
  LAN is typically within a few ms, over the internet tens of ms; PTP is
  better. Same-machine runs have no such error.
- A pattern generated on the box says nothing about the camera, HDMI capture
  or the capture card; that needs the pattern played over HDMI.
- The first and last seconds are not judged (startup bursts, cut recordings).
- Passive figures (`idet`, `mpdecimate`, `blockdetect`) depend on the
  content; the pattern-based checks are the reliable ones.
